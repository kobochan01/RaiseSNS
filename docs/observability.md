# 運用監視・障害対応設計書

## 1. 目的

障害の早期検知と原因調査の迅速化を目的に、バックエンドの構造化ログ基盤を整備する。現時点ではログを標準出力にJSON形式で出すところまでが対象で、将来Datadog Agentを接続すればすぐにログ収集を開始できる状態を作ることがゴール。Datadog Agent自体のセットアップ（インストール、APIキー設定）は本設計書のスコープ外。

## 2. ログ設計

バックエンド（Spring Boot）は`logstash-logback-encoder`により、全ログを1行1JSONの構造化形式で標準出力へ出力する（`backend/src/main/resources/logback-spring.xml`）。

主なフィールド：

| フィールド | 内容 |
|---|---|
| `@timestamp` | ログ出力時刻 |
| `level` | ログレベル（INFO/WARN/ERROR） |
| `logger_name` | 出力元クラス名 |
| `message` | ログメッセージ |
| `stack_trace` | 例外発生時のスタックトレース |
| `service` | サービス名（`backend`。`spring.application.name`から取得） |
| `env` | 環境名（環境変数`DD_ENV`。未設定時`local`） |
| `version` | アプリバージョン（環境変数`DD_VERSION`。未設定時`unknown`） |
| `traceId` | リクエスト単位の追跡ID（後述） |

`service`/`env`/`version`はDatadogのUnified Service Tagging規約に沿ったフィールド名にしており、将来Datadog Agent経由でログを収集した際にAPM・メトリクスと自動的に紐付く。

## 3. ログレベル運用方針

- **INFO**：通常のリクエスト完了ログなど、正常系の記録
- **WARN**：4xx系のクライアント起因エラー（バリデーション失敗、認証エラー、404、403など）。`GlobalExceptionHandler`の各ハンドラで出力
- **ERROR**：5xx系のサーバー・外部依存起因エラー（S3アップロード失敗など）、および想定外の例外。スタックトレースを必ず含める

## 4. リクエスト追跡（traceId）

`RequestLoggingFilter`（`com.raisesns.backend.logging`）が全リクエストに対しUUIDの`traceId`を発行し、MDCにセットする。これによりリクエスト処理中（認証・コントローラ・例外ハンドラ）に出力される全ログ行に自動で`traceId`が付与される。

同じ値をレスポンスヘッダー`X-Request-Id`としても返すため、フロントエンドやクライアント側で問題が発生した際にこのIDを控えておけば、バックエンドのログをそのIDで串刺し検索して該当リクエストの処理内容を特定できる。

## 5. Datadog連携（現状と将来）

**現状**：Datadog Agentは未接続。ログは標準出力にJSON形式で出力されるのみ。

**将来接続する際の想定手順**：

1. Datadog Agentをアプリと同じホスト/コンテナ環境に配置し、標準出力（またはログファイル）を収集対象に設定する
2. 環境変数`DD_ENV`（例：`production`）・`DD_VERSION`（例：デプロイのgit sha or リリースタグ）を設定する（アプリの再ビルド不要、環境変数の追加のみ）
3. Datadog側でログのJSONパイプラインを設定し、`service`/`env`/`version`/`traceId`などのフィールドをファセットとして認識させる
4. 必要に応じてログベースのモニター（例：`level:error`が一定件数を超えたらアラート）を設定する

アプリ側にAPIキーやDatadog固有のSDK・エージェントを組み込む必要はない。

## 6. 障害対応フロー（runbook）

1. **検知**：現状は手動でのログ確認が中心。Datadog接続後はログベースのモニター/アラートによる自動検知に移行する
2. **調査**：エラー発生時刻・エンドポイント、またはクライアントから報告された`traceId`（レスポンスヘッダー`X-Request-Id`）でログを検索する
3. **原因切り分け**：該当`traceId`のログ行を時系列で追い、`stack_trace`から例外発生箇所を特定する
4. **復旧対応**：原因に応じてアプリの修正・再デプロイ、または外部依存（DB、S3等）側の復旧を行う
5. **記録**：対応内容を`DEVELOPMENT.md`のエラーログ表に追記し、再発防止の知見を残す

## 7. 今後の拡張候補

本設計書のスコープ外だが、将来的に検討する項目：

- Datadog APM（分散トレーシング）の導入
- Micrometer経由のメトリクス収集とDatadogダッシュボード化
- ログベース以外のモニター（レイテンシ、エラー率などのメトリクスベースのアラート）
- Datadog Agentの実際のデプロイ構成（EC2上へのインストール、コンテナ化する場合のサイドカー構成など）
